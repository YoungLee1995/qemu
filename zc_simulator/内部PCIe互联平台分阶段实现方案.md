# 内部 PCIe 互联平台分阶段实现方案

## 1. 目的与依据

本文为内部仿真实验平台的实现建议，供 simu 组拆分任务、开展技术验证和组织验收使用。本文及后续 AI 辅助实验产物不用于 QEMU 上游贡献，遵循 [QEMU 内容来源政策](../docs/devel/code-provenance.rst)。

输入文档：

- [NCCL 仿真平台需求决策记录](nccl-simulator-decisions.md)：确定首版范围、最新取舍和待确认事项。
- [8 卡单 PCIe Switch Simulator 需求](pci-switch-8card-simulator-requirements.md)：提供协议、地址、流量和测试需求基础。

两份基础文档存在差异时，以决策记录中的最新结论为准；本次补充的执行方式以需求方最新说明为准：工具链下发信息包给 runtime，由 runtime 逐笔生成 simu 执行动作，不预加载完整业务指令段。下文的架构、阶段、接口和验收用例属于实施建议，不能视为已有能力或已确认的硬件规格。

实施主线为：**接口冻结 → 单卡软件闭环 → 双卡互联 → 八卡功能平台 → 多 die 扩展 / 性能建模**。首版在第四阶段结束；后两项分别立项，互不构成强制前置条件。

## 2. 首版交付边界

| 项目 | 首版要求 | 实施解释 |
| --- | --- | --- |
| 主机环境 | x86、Linux、单 NUMA 节点、一个 Root Complex | 建议使用 Q35 和 TCG 起步；KVM 不作为门槛；不限定物理 CPU 型号 |
| PCIe 拓扑 | 一个 switch、八个下行端口、八卡，每卡一 die | 开发时按一张、两张、八张逐步扩展，最终必须八张 |
| NPU | 集成自研单 die 4 core 完整 simu | 首版八卡共 32 个 NPU core；完整组件边界仍需盘点，不沿用旧文档的单核最小模型假设 |
| Device 软件 | MCU 实际运行常驻 runtime，接收工具链信息包并逐笔驱动 NPU | 固件/runtime 允许启动加载；业务执行不依赖预加载完整指令段；保留 MCU/NPU mailbox |
| 业务提交 | 工具链 → 主机提交接口 → PCIe → runtime → 单笔执行动作 | 信息包格式、单笔粒度和完成语义在第一阶段冻结；接收成功不等于执行完成 |
| 数据搬运 | NPU DMA、PCIe HDMA | 覆盖固件/模型加载、主机内存访问、卡间访问；MCU DMA/HSDMA 非必需 |
| 地址转换 | 主机 IOMMU、inbound/outbound ATU | 主机 DMA 使用 IOVA；同 switch P2P 绕过主机 IOMMU；设备侧不启用 SMMU |
| 软件兼容 | 优先匹配真实硬件驱动和已有 demo | 所有 workaround 单独记录原因、范围和恢复条件 |
| 正确性 | 数据、队列、完成通知、错误和复位行为 | 必须验证正常流程所需的顺序、权限、超时和错误处理 |
| 性能 | 首版只记录功能诊断及宿主资源消耗 | 不承诺链路带宽、延迟、拥塞或周期精度 |

平台提供通用互联与设备运行能力，通信库可作为外部验收工作负载接入。平台不承担 collective 算法、CCL transport、proxy、kernel 或算子实现。

## 3. 推荐架构与职责

### 3.1 系统组成

```text
运行平台的物理主机
├─ QEMU：x86 Q35 / TCG
│  ├─ 来宾 Linux（需求文档中的 Host OS）
│  │  └─ 工具链信息包提交端、原硬件驱动、demo、外部通信库测试
│  ├─ Root Complex + 来宾可见的 Host IOMMU
│  └─ Root Port → Switch 上行桥 → 八个下行桥
│     └─ PCIe EP 0..7：配置空间、BAR、ATU、DMA 适配、中断
└─ 既有 device simulator（集成方式待第一阶段验证）
   └─ Card 0..7，各一个完整 die
      └─ MCU / runtime / mailbox / NPU / NPU DMA / local memory
```

这里的 Host IOMMU 是来宾 Linux 管理的仿真 IOMMU，并非运行 QEMU 的物理主机 IOMMU；主机物理地址指来宾物理地址 GPA。不能将 GPA、宿主进程指针和设备本地地址混为一类。

建议先复用 QEMU 的主机、PCIe 枚举和 IOMMU 能力，新增内部 EP 与设备模型适配层。功能版的 switch 使用桥层级表达连接关系，跨卡请求经受控路由层检查端口、窗口和目标 EP。后续性能版再增加显式链路、队列和事务调度，不能把现有桥模型等同于 TLP/credit 精确仿真器。

### 3.2 模块职责与状态归属

| 模块 | 负责内容 | 状态归属原则 |
| --- | --- | --- |
| 主机平台 | Linux 启动、PCIe 枚举、IOMMU、地址资源分配 | 来宾驱动维护映射，QEMU IOMMU 实现转换和失效处理 |
| EP 适配层 | 硬件配置空间、BAR、ATU、doorbell、中断、HDMA 接口 | 可见寄存器按硬件契约实现；后端持有的状态通过协议同步 |
| 功能路由层 | 区分 HOST_IOVA / PEER_BAR / DEVICE_LOCAL，检查目标窗口、权限和 P2P 开关 | 不自建另一套与来宾脱节的主机 IOMMU 页表 |
| runtime 命令处理 | 接包、校验、目标 core 选择、参数/描述符准备、逐笔提交、完成与错误回传 | 运行在设备 MCU；定义包生命周期；不能由 Host 直接调用模型代替最终验收 |
| 设备后端 | 单 die 4 core NPU、MCU 执行、mailbox、本地内存、NPU DMA 与动作接入 | 复用现有执行/计算/内存语义；本地内存只有一个权威存储；BAR/HDMA/NPU 访问同一份数据 |
| 连接适配 | 请求与响应、事件、取消、错误、复位代次 | 有界队列、请求 ID、版本协商；断连不能永久挂住 QEMU |
| 测试与观测 | 配置、启动、数据校验、日志关联、回归和结果归档 | 一份运行清单关联驱动、固件、模型、配置和日志 |

PCIe HDMA 的具体执行逻辑放在 EP 还是设备后端，按既有模型能力在第一阶段定案。NPU DMA 也只保留一个执行责任方，避免同一请求被两侧重复执行。

### 3.3 集成方式的决策点

优先验证“一个 QEMU 进程 + 每卡一个 device simulator 进程”，方便单卡调试和八卡实例隔离；这只是候选方案，不代表 socket 或进程粒度已经定案。

第一阶段比较进程内调用与本地 IPC 两种方式，依据包括：既有 simulator 是否支持多实例、线程和回调约束、MCU 执行方式、本地内存规模、故障定位和数据交换开销。若使用 socket，先传输控制消息和有界数据分片；只有测得复制开销构成瓶颈后再评估共享内存，届时必须定义所有权与可见性。

建议连接契约至少包含：

- 协议版本、card/die 标识、能力查询、启动/停止/复位。
- MMIO/BAR 访问、ATU 更新、设备内存访问、HDMA/NPU DMA 请求与结果。
- mailbox、doorbell、中断、runtime 就绪和错误事件。
- 信息包提交与接收确认、逐笔执行完成、队列满和无效包错误；端到端命令 ID 与连接请求 ID 的关联。
- 请求 ID、复位代次、地址域、长度、方向、状态、可选数据。
- 超时、取消、断连后的失败响应以及旧代次响应丢弃规则。

QEMU 事件上下文负责寄存器和中断状态更新；外部回调通过事件投递接入，不能在 MMIO 回调里无限等待 socket，也不能让后端线程直接修改 QEMU 设备状态。明确“DMA 数据提交可见 → completion 更新 → 中断通知”的顺序。

### 3.4 从完整程序加载转为信息包驱动执行

#### 已有示例的含义与限制

参考工程位于工作区 `moe_bf16_sint4_33x29x34_fix/`，属于旧模式的功能参考：

- `run.sh` 调用固定 `/data/ci/...` 路径下的 Spike 与 `firmware.riscv`，传入相对路径 `simulator.cfg`；迁移后需确认本地二进制、工作目录和 SDK 依赖。
- `simulator.cfg` 指定 hart 16（NPU0）从 `0x20000000` 执行完整业务 `.bin`，加载四份 L1 输入，导出 `0x10009200` 起的 33792 字节结果。
- `test_moe.cc` 调用 `matmulMoeQuant`，`descriptor.txt` 给出 Tensor 参数；完整 `.bin` 还包含启动和辅助指令，不能把整个文件视作一笔 NPU 指令，也不能认为描述符文本就是工具链包协议。
- 现有 firmware 在 `simulator/riscv-tests/firmware/firmware.c` 中读取数据和程序文件，配置 dispatcher 入口后启动 NPU；现有 Spike 在 `riscv/execute.cc` 中取指、译码并执行。

这些是静态代码观察，尚未在当前环境重建或运行。示例用作数据、描述符和结果参考，不作为新模式的运行接口。

#### 目标链路

```text
启动阶段：加载固件 / MCU runtime / 必要的常驻执行支撑代码 → runtime READY
数据阶段：Host 分配并映射内存 → HDMA / NPU DMA / BAR 搬入或按需读取数据
业务阶段：工具链产生信息包
          → 来宾 Host 提交端 / 驱动
          → PCIe 命令队列或 BAR + doorbell（具体机制待定）
          → MCU runtime 接收、校验、解析
          → 选择 card/die/core，准备描述符与上下文
          → 单笔 NPU 动作提交 → 模型执行 / DMA → 真实完成
          → runtime 写 completion → PCIe 通知 → Host 消费结果
```

工具链可离线生成包，Host 提交端可回放；工具链本体不必运行在来宾内。业务包协议与 QEMU/simu 连接协议属于不同层次，前者不能因选择 socket 而被后者替代。

“不预加载完整指令段”针对业务程序，仍需加载 MCU/runtime 以及必要的执行支撑代码，也仍需准备输入、权重和输出缓冲。若模型需要从内存取指，可评估 runtime 动态写入有界的单动作指令片段，再交给常驻执行器；必须处理指令可见性、取指缓存、寄存器上下文和完成条件，不能退回每包加载整段 kernel 的方式。

#### 必须冻结的执行契约

| 问题 | 首轮需明确的内容 |
| --- | --- |
| 单笔指令的粒度 | 一条 ISA 指令、一个 DSA/Tensor/DMA 动作，还是含设置步骤的命令；一包与动作数量的关系尚未确认 |
| 信息包内容 | 采用真实工具链格式；定义版本、长度、操作类型、命令 ID、目标 core、参数/描述符、地址及长度；哪些字段来自上下文要明确 |
| 参数与数据 | 区分包内参数、设备描述符指针、Host IOVA 和 peer 地址；定义端序、对齐、生命周期及权限，不传宿主指针 |
| runtime 的责任 | 明确包由工具链编码到何种程度，runtime 负责解析/补参还是生成指令；不把完整编译器实现纳入互联平台 |
| 模型提交入口 | 优先复用已有合法执行入口；若新增动作接口，要保留操作语义、core 上下文、内存访问、调度及错误路径 |
| 完成时机 | 分开记录接收、提交与执行完成；ISA 退休或动作入队不一定表示异步计算/DMA 结束；完成后结果必须可见 |
| 常驻与隔离 | 同一进程/runtime 可连续处理多包；目标 core 状态独立；单笔完成不退出整个仿真 |
| 顺序与恢复 | 先支持单队列单 outstanding，再扩展并发；明确依赖、重复包、队列满、超时、取消与复位代次 |

首轮可用测试提交端替代尚未交付的工具链发送端，但必须使用已对齐的包格式并经过真实 runtime；直接调用 C++ 计算接口仅用于定位和对照，不能替代最终链路。现有 mailbox 测试只证明通知能力，不证明已具备包解析和逐笔动作执行能力。

## 4. 地址与访问路径

### 4.1 必须区分的地址域

| 地址域 | 含义 | 使用场景 |
| --- | --- | --- |
| HOST_IOVA | 来宾驱动为请求设备建立的 DMA 地址 | 设备读写来宾 Linux 的内存 |
| HOST_GPA | 来宾物理地址，含已分配的 PCIe BAR 窗口 | IOMMU 转换结果、主机 MMIO、PCIe 目标地址 |
| PEER_BAR | 目标卡的 PCIe 总线 BAR 地址及偏移 | P2P 路由；首版需核实总线地址与 GPA 的关系 |
| DEVICE_LOCAL | 某个 card/die 内的本地地址 | NPU/MCU 内存访问和 inbound ATU 目标 |

平台内部标签用于检查和 trace，不得要求原驱动额外传入真实硬件没有的标签。分类依据应来自硬件窗口、ATU 配置和请求上下文；窗口重叠、匹配优先级、读写权限和未命中行为需在接口契约中明确。

### 4.2 三条基本路径

1. **Host 访问设备**：来宾 CPU MMIO → PCIe BAR 解码 → inbound ATU（按硬件适用范围）→ 设备寄存器/本地内存。HDMA 加载按实际描述符和引导协议进行，不能提前假定由尚未启动的 runtime 发起自身加载。
2. **设备访问 Host 内存**：设备 DMA → outbound ATU → HOST_IOVA → 请求设备对应的 QEMU IOMMU 地址空间 → GPA → 来宾内存。保留 requester/BDF、权限、跨页分片和失效语义，不允许通过宿主指针复制绕过转换。
3. **设备访问另一设备**：源设备 DMA → outbound ATU → 目标 BAR 总线地址 → switch 功能路由 → 目标 BAR / inbound ATU → 目标本地内存。该路径不调用主机 IOMMU 转换，仍检查端口连接、桥窗口、P2P 开关、目标权限和 Bus Master 等条件。

第二、三条路径的选择及 ATU 输出含义必须和真实硬件核对；上面给出逻辑链条，不预定 ATU 寄存器布局。

### 4.3 P2P 与 IOMMU 的关键验证

QEMU 的 `pci_dma_*` 使用设备 DMA 地址空间，不能假设传入目标 BAR 地址就自然绕过 IOMMU。第三阶段前必须证明双卡 P2P 的真实访问路径；若现有路径不能表达需求，需实现范围受限的内部 peer 路由。

该路由只能命中当前拓扑中启用的目标 BAR 窗口，复用目标 BAR/ATU 的访问逻辑；不能开放任意 GPA 直访，也不能全局关闭 IOMMU来“实现”P2P。桥窗口和 BAR 重定位后更新路由，禁用目标解码后访问失败。

验证时同时开启 IOMMU，检查主机 IOVA 权限错误仍失败，而目标 BAR 未建立 IOVA 映射时合法 P2P 仍成功。Linux P2P 接口、驱动地址下发方式、ACS 重定向能力及其配置要分别核实并记录；不能把驱动 workaround 误当成硬件行为已实现。

## 5. 分阶段实施与验收

### 第一阶段：资料对齐与关键风险验证

**目标**：在投入完整 EP 开发之前，固定一套可运行的软件与模型基线，消除 runtime 和地址路径的不确定性。

工作内容：

1. 从 Jonathan 对接硬件/驱动资料，从 Linden 或 Hecl 获取已跑通的 VPS/ZeBu demo、启动步骤和参考输出；资料到位情况逐项登记。
2. 固定驱动、Linux、固件、runtime、NPU 模型及工具链版本；盘点完整单 die 组件、MCU ISA、内存布局和模型依赖。
3. 整理配置空间、BAR 大小/类型、ATU、HDMA、NPU DMA、mailbox、中断、复位和加载时序；每项标注依据、缺口和验证方法。
4. 启动 x86 Linux + 仿真 IOMMU；验证 simulator 单实例启动与最小请求/事件往返；形成双卡 P2P 路径的源码分析和最小实验设计。
5. 定案进程组织、协议、内存归属、事件调度与功能顺序语义；确认 barrier 是否为目标工作负载前置条件。
6. 优先完成第 10 节的单 die 信息包闭环验证，冻结单笔粒度、真实工具链包样本、runtime 入口、模型动作入口及完成条件。该实验不等待 PCIe EP 开发。

**交付物**：接口对照表、版本清单、启动基线、单笔执行接口对齐表与验证记录、集成决策记录、P2P 风险验证记录、待办清单。

**通过门槛**：真实 runtime 可接收至少一类信息包，驱动模型完成动作并返回可校验结果，且可连续处理两包而不重启；runtime 有明确可执行路径；完整模型可获取且有启动证据；核心寄存器和 DMA/中断协议可据以开发；未确认项有责任方和关闭条件。资料不足时可继续拓扑实验，但不宣称真实驱动/runtime 兼容。

### 第二阶段：单卡驱动与 runtime 闭环

**目标**：一张卡完成从 Linux probe 到 runtime/NPU 执行的真实软件路径。

工作内容：

1. 构建一条 switch 下行连接和一个内部 EP，完成 PCIe 配置空间、BAR、Bus Master、驱动所需中断和复位行为。
2. 接入单卡完整 die，完成本地内存、ATU、doorbell 和 MCU/NPU mailbox。
3. 按实际引导协议通过 PCIe HDMA 加载固件/runtime 和所需数据；MCU runtime 常驻就绪。接入工具链信息包的 Host 提交、PCIe 传输、runtime 解析、逐笔动作执行及完成回传，不以加载完整业务 `.bin` 代替。
4. 通过来宾 Linux DMA 映射 API 建立 IOVA，打通 NPU DMA 对主机内存的双向访问；实现描述符边界、请求状态和失败返回。
5. 验证数据可见后才完成通知；复位取消或终止旧请求，晚到结果不会污染新运行。

**交付物**：单卡启动配置、EP/后端适配实验实现、驱动差异表、单卡回归脚本及关联 trace。

**通过门槛**：probe → BAR/中断配置 → HDMA 加载 → MCU/runtime 就绪 → 工具链信息包经 PCIe 到达 runtime → 单笔 NPU 动作执行完成 → 结果与 DMA 数据校验全链路通过；未映射 IOVA、只读映射写入、越界和复位中请求有明确结果。单独的 EP stub 冒烟通过不等于此阶段通过。

### 第三阶段：双卡 P2P 与地址隔离闭环

**目标**：证明主机 IOMMU DMA 与卡间 P2P 可以同时正确运行。

工作内容：

1. 增加第二个下行端口和完整设备实例，实现目标 BAR 查找、ATU 配合和请求/响应归属。
2. 验证 A→B、B→A 的读写与双向并发，覆盖窗口首尾、跨边界、不同长度与非对齐访问（是否允许按硬件规定）。
3. 同时发起 HOST_IOVA 和 PEER_BAR 请求，检查前者经过 IOMMU、后者不经过 IOMMU，且均未误投递。
4. 覆盖 P2P 禁用、非法目标、窗口关闭、BAR/ATU 重配置和目标复位；明确在途请求采用完成、取消或失败中的哪种硬件允许语义。
5. 完成 IOMMU 映射撤销及必要失效同步后，发起新 DMA 必须失败；撤销前已在途请求按硬件契约判定，不能统一要求追溯失败。

**交付物**：双卡互联配置、地址/路由设计定稿、IOMMU 与 P2P 混合回归、错误与恢复记录。

**通过门槛**：双卡读写数据正确；P2P trace 无主机 IOMMU 转换；主机 DMA fault 能归属正确请求设备；非法 peer 地址不能落入主机内存；同一请求不重复完成，失败不会永久挂起。

### 第四阶段：八卡首版功能平台

**目标**：交付八卡 × 一 die 的内部功能基线，供现有通信软件联调。

工作内容：

1. 统一生成八卡配置、端口/BDF、桥窗口、BAR 资源和实例标识；确认 Linux 可分配全部 BAR 和总线资源。
2. 启动八份完整 die 模型与常驻 runtime，验证每卡四个 NPU core 均可按包寻址执行，检查内存、队列、中断、trace、复位代次相互隔离。
3. 覆盖全部 56 个有向卡对读写、八卡同时访问主机内存、八卡 all-to-all 数据搬运；先使用通用流量测试，再接入已有通信库 demo。
4. 对多个 outstanding 请求检查数据、完成归属、顺序、错误和超时；故障处理以已确认硬件行为和必需的仿真连接错误为范围。
5. 对单卡 runtime 异常、后端断连、DMA 超时和复位执行恢复回归；记录其他卡的影响范围。
6. 固定启动与回归入口，归档版本、配置、输入种子、日志和数据校验；测量宿主内存、CPU、启动耗时与回归耗时，作为容量基线。

**交付物**：八卡功能版、运行说明、配置样例、自动回归、验收报告、已知差异和限制清单。

**通过门槛**：第 6 节全部首版用例通过；完整单 die 模型未被裁剪；八卡 runtime 均可运行；外部 demo 的约定场景通过。若 demo 或依赖资料尚未交付，必须标记“软件联调未验收”，不能以流量发生器替代最终结论。

### 第五阶段：单卡多 die 扩展（独立后续工作）

**目标**：由八卡八 die 扩展至八卡六十四 die，支撑 runtime 下的已有简单存算融合算子与网络 kernel 流图。

先对一张卡进行 1→2→8 die 扩展，补充卡内互联、内存归属、队列/中断路由、同步与复位域，再扩展八卡。每 die 优先评估完整 4 core；是否允许 1 core、如何回退及受影响的功能，需要单独确认，不能直接改变首版完整单 die 要求。

**通过门槛**：完成 1/2/8/64 die 容量曲线；在约定资源预算下跑通目标 runtime/已有 kernel 流图；给出数据正确性、同步、死锁与恢复结果。核数、算子清单、资源上限和可接受运行时间须在该阶段开工前确定。

### 第六阶段：PCIe 事务与性能模型（独立后续工作）

**目标**：在已稳定的功能路径上增加可校准的事务、链路和拥塞模型。可基于八 die 功能版推进，无须等待六十四 die。

按以下顺序开展：

1. 将功能 DMA 分片映射成显式事务，定义 Read/Write/Completion、tag、MPS/MRRS、错误及顺序规则；posted write 不虚构 PCIe Completion，DMA 完成与 PCIe Completion 分开定义。
2. 增加每链路 generation/width、协议开销和传输时间模型，明确时间单位、虚拟时钟与设备执行时间的关系。
3. 增加 Posted/Non-Posted/Completion 缓冲、Header/Data credit、返还和 backpressure。
4. 增加 round-robin、fixed priority、weighted round-robin 仲裁及共享上行/下行竞争；实现规范允许的 relaxed ordering 和可配置延迟。
5. 加入 UR、Completion timeout、阻塞等约定错误注入，导出利用率、队列占用、stall 和延迟分布。
6. 与硬件测量、参考模型或协议推导结果校准，确定误差口径、样本和容差。

**通过门槛**：功能回归继续通过；带宽/延迟可解释并满足预先约定的校准容差；credit 守恒、恢复不死锁；相同输入与调度种子下仿真结果可重复。QEMU 墙钟耗时或 socket 吞吐不能作为模拟 PCIe 带宽。

## 8. 关键风险与关闭条件

| 风险 | 对首版的影响 | 关闭条件或处理方式 |
| --- | --- | --- |
| 信息包与单笔粒度不明 | 无法选择执行接入层 | 取得真实工具链样包，逐字段关联 runtime 与模型动作；不自行发明最终 ABI |
| 模型只有完整程序取指入口 | 单笔提交无法直接接入 | 比较常驻执行器/动态短片段与动作提交接口，验证上下文和异步完成语义 |
| 完整单 die 模型的组件和接口不明 | 无法评估接入工作量 | 形成组件/接口清单并单实例跑通；不得自行裁剪 |
| MCU ISA/固件/runtime 执行能力缺失 | 无法完成真实软件闭环 | 确认已有执行模型和 image；源码适配须记录差异；stub 只用于早期调试 |
| IOMMU 开启时 P2P 路径不成立 | 核心互联目标受阻 | 双卡实验验证受限 peer 路由与主机 DMA 隔离 |
| BAR 容量或桥窗口不足 | 八卡无法全部枚举和使用 | 核实 32/64 位 BAR、预取属性和固件资源分配；提前做八卡资源实验 |
| 重复维护本地内存或重复执行 DMA | 数据不一致或重复完成 | 指定唯一状态所有者，统一请求 ID 和复位代次 |
| IPC 等待与中断回调相互阻塞 | Linux 或设备挂起 | 有界请求、异步事件和超时；验证断连及复位 |
| Barrier/完成通知语义未定 | 部分通信工作负载不能运行 | 由需求方确认所需语义；只验收已定义的通知机制 |
| 八份完整模型资源消耗过大 | 八卡运行速度或容量不足 | 第二阶段测单实例、第四阶段测八实例；评估调度和存储优化，不默认删减模型 |
| 性能口径混入功能验收 | 首版范围失控或产生错误结论 | 将宿主运行成本、仿真功能时间和硬件性能指标分别报告 |

## 10. 当前第一步：单 die 信息包执行闭环

具体操作、代码入口、实验模块及验收步骤见[单 die 信息包执行闭环实施指南](单die信息包执行闭环实施指南.md)。

### 10.1 第一项任务与产物

先完成《单die信息包执行接口对齐清单》，范围限定为一张卡、一个 die、选定一个 NPU core、一类动作。先追通本地真实 runtime 与模型，再把同一提交路径接到 PCIe；第一步不扩八卡、不实现性能模型。

执行顺序：

1. **建立旧模式参考。** 固定当前 Spike、firmware、配置、业务 bin 和输入文件版本，在示例目录重现 MoE 用例并保存新生成的输出。启动脚本应使用本地明确路径、检查流水线各命令的退出状态，避免把旧结果或最后一行完成提示当成功。该项只建立参考，不是目标功能验收。
2. **拿到最小真实信息包。** 向工具链/runtime 提供方取得一份实际包字节及字段说明，明确它代表什么动作、哪些状态须提前设置、由谁生成描述符。优先选择该示例中可以独立提交的 Tensor 动作；若该动作必须依赖其他设置操作，先列出依赖，或选择协议已支持的更小动作，不能直接截取完整 bin 的某几个字节。
3. **做字段到入口的静态追踪。** 从 `test_moe.cc` 的 `matmulMoeQuant`、`descriptor.txt` 和反汇编定位参数准备及实际操作，再追到指令 handler、`smart/sm_npu.cc` 等模型入口。并行检查 runtime 的收包、解析和动作提交代码是否存在；现有 `runtime_test/runtime_src` 主要提供 mailbox/ECLIC 资料，不能假定是完整命令 runtime。
4. **选定最小接入方式。** 按第 3.4 节对齐粒度，确认复用现有执行入口还是需要有界单动作执行适配，记录 PC/寄存器/描述符、内存和异步完成处理。真实 runtime 缺失时先形成接口缺口清单，不能用直接 C++ 调用宣称闭环通过。
5. **做本地收包闭环。** 启动一次 MCU/runtime 与完整单 die 模型，初始化输入数据，由测试提交端经过确定的收包入口发送一包，runtime 生成动作，等待模型真实完成并读回结果。随后再发第二包，验证不重启且无重复执行、上下文污染；包内容尚未产生时不提前写死传输 ABI。
6. **对齐结果与错误。** 使用同样输入和执行语义比较新旧路径；该 MoE 示例预期输出为 33792 字节，先核对大小与布局，再比较完整有效输出（含零值、NaN/Inf 规则及约定的数值容差）。原 `check_result.py` 会截取较短长度并过滤部分数值，不能作为唯一验收依据。补充非法包与错误 core 目标，验证有错误返回且未执行动作。

### 10.2 接口清单必须回答的问题

| 项目 | 首轮记录内容 |
| --- | --- |
| 包格式与来源 | 工具链版本、样包、字段/端序/长度、协议负责人 |
| 提交粒度 | 一包对应的动作、前置设置、目标 core 与依赖 |
| runtime 接入 | 具体源码/函数、运行 hart、收包入口、解析与提交调用链 |
| 模型接入 | 具体 handler/函数、参数、执行上下文、推进调度方式 |
| 数据归属 | 输入/输出/描述符地址、地址域、分配与可见性 |
| 完成与失败 | 接收确认、动作完成信号、结果可见时机、错误和复位处理 |
| 复现证据 | 命令、配置/二进制版本、新生成结果、逐包 trace、两包连续执行结果 |

通过标准：真实 runtime 已按包生成并执行动作；复用真实模型语义；不预加载完整业务指令段；同一实例可处理连续两包；数据和失败行为可校验。若只完成样例复现、mailbox 通知或模型直调，应按实际完成项报告。

随后第二步才是将本地测试提交端替换为“来宾 Host → 驱动 → PCIe EP → runtime”，保留同一信息包语义、模型入口和完成定义，并接入 IOMMU/ATU 与 HDMA/NPU DMA 数据路径。
