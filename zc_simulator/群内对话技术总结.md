# NCCL 仿真平台需求决策记录

## 1. 文档说明

本文整理内部讨论中已确认的需求、后续演进目标和待确认事项，供 simu 组承接 NCCL 仿真平台工作使用。

- 人力安排：simu 组暂时投入 1 人承接，前期先确定需求大方向。
- 需求基础：[8 卡单 PCIe Switch Simulator 需求](pci-switch-8card-simulator-requirements.md)。该文档前两部分已获讨论方认可，认为基本覆盖主要问题；后续讨论进一步调整了部分范围。
- 本文按对话中的最新结论记录；涉及既有文档中已被调整的内容，见第 6 节。
- 本文是内部平台的需求记录，不代表 QEMU 上游功能承诺，也不表示所列能力已经实现。

## 2. 首版已确认的决策

| 主题 | 已确认结论 | 范围说明 |
| --- | --- | --- |
| Host CPU | 基于 x86 即可，当前无明确型号要求 | 暂不指定 AMD EPYC 或 Intel Xeon 型号 |
| 执行方式 | KVM 加速首版可以不支持 | 首版不以 EPYC 9654 工作站的 KVM 环境或 IT 配置支持为前置条件 |
| Host OS | 主机端启动 Linux，业务在 Linux 上运行 | 现有 VPS、ZeBu 环境已有可运行 demo，可作为对齐参考 |
| 卡间拓扑 | 单 NUMA 节点、一个大 PCIe switch、8 张卡 | 首版优先覆盖此拓扑 |
| 多 switch / NTB | 首版不支持 | 两个 switch 间的 fabric 通路及 NTB 实现暂不纳入 |
| 每卡 die 数量 | 首版每卡 1 die，共 8 die | 暂不建立单卡 8 die 的内部拓扑 |
| 单 die NPU 模型 | 按最新讨论，单 die 的 NPU 模型不再裁剪 | 替代前期仅保留单核、基础 NI900 和 DMA 的最小模型设想；现有模型具体组成仍需对齐 |
| MCU 与 runtime | Device 侧需要 MCU，并能够运行 runtime | 需支持 MCU 与 NPU 的 mailbox 通信 |
| NPU DMA | 需要 | 已明确需求是 NPU 侧 DMA |
| PCIe HDMA | 需要 | 用于加载固件和模型 |
| MCU DMA / HSDMA | 可以没有 | 首版不要求实现这些 DMA 模块 |
| Host IOMMU | 需要主机侧 IOMMU 能力 | 服务于主机加载固件、设备运行等相关流程，具体映射方式需按驱动与 demo 对齐 |
| 卡间 P2P | 通过 PCIe P2P 通信，不经过 Host IOMMU 地址转换 | 建模时需区分访问主机内存与访问其他设备的路径 |
| PCIe 地址转换 | 需要模拟 inbound / outbound ATU 地址转换 | 与 BAR、设备地址窗口和路由行为配合；具体参数待硬件资料对齐 |
| 驱动兼容性 | 优先按真实硬件行为实现，尽量保持软件驱动代码一致 | 确实无法一致时允许软件 workaround，差异需在接口对齐时明确 |
| 首版验证重点 | 以功能正确性为主 | PCIe 带宽、延迟、拥塞等性能建模放到下一步 |

### 2.1 首版拓扑

```text
x86 Host / Linux / Host IOMMU
               |
       PCIe Root Complex
               |
       单个 PCIe Switch
               |
     +---------+---------+ ... +---------+
     |                   |     |         |
   Card 0              Card 1  ...     Card 7
   1 die               1 die          1 die
```

Device 侧需要覆盖 MCU、NPU 模型、MCU/NPU mailbox、NPU DMA、PCIe HDMA，以及 runtime 运行所依赖的能力。首版采用 8 卡 × 每卡 1 die，不是 8 卡 × 每卡 8 die。

### 2.2 驱动与硬件行为对齐

讨论确认优先依据真实硬件及已有驱动/demo 建模。重点对齐的典型流程为：

```text
probe → 配置 BAR → 使能中断 → 发起 DMA → 处理中断
```

该流程是驱动对齐的参考主线；具体 PCIe 配置空间、寄存器、DMA 描述符、中断类型和固件加载协议，仍需从 demo 和硬件资料中确认，不能仅凭本次对话确定。

## 3. 后续演进目标

| 阶段 | 目标 | 边界与条件 |
| --- | --- | --- |
| 首版 | 支持当前 NCCL/通信库仿真平台，8 卡、每卡 1 die，单 die NPU 模型不裁剪 | 功能优先，支持 Linux 主机端、device runtime 及所需 DMA/通信能力 |
| 后续功能扩展 | 每卡扩展到 8 die，共 8 卡 64 die，通过 runtime 运行简单的存算融合算子及完整网络 kernel 流图 | 需要补充单卡多 die 拓扑与相关通信建模，并评估整体仿真负载 |
| 后续性能建模 | 建模带宽、延迟、拥塞等性能行为 | 本次未确定性能精度、指标或交付时间 |

后续多 die 方案中，需求方希望每 die 完整支持 4 core；如果负载或实现条件不允许，可考虑每 die 1 core。讨论尚未将这一偏好确定为最终交付规格。

“负载太重时复用上面的模型”是讨论中的回退方向，具体复用哪种模型、如何裁剪及对 kernel 流图的影响，仍需在扩展阶段明确。现阶段没有完成对 8 卡 64 die、每 die 4 core 的可行性验证或性能承诺。

## 4. 尚未定案的事项

| 事项 | 当前状态 | 下一步需要确认的内容 |
| --- | --- | --- |
| Barrier 同步指令 | Jonathan 表示还需考虑，未形成结论 | 是否实现 barrier 指令；device 间完成通知是否采用软件中断；所需同步语义 |
| QEMU 与既有 simulator 集成 | 已提出在 QEMU PCIe EP 代码中连接既有 simulator，例如通过 socket 通信 | 是否采用该方案、连接粒度、进程组织、协议与事件/中断传递方式；socket 尚非已定接口 |
| 单 die 完整 NPU 模型边界 | 最新结论是不裁剪，但未列出完整组件清单 | 既有模型的核数、计算单元、内存及执行能力，运行目标 runtime/kernel 还缺哪些能力 |
| 多 die 核数和模型回退 | 优先完整 4 core，允许评估 1 core 方案 | 目标负载、资源开销、功能覆盖及回退条件 |
| 硬件/软件接口细节 | 已确认优先按真实硬件对齐 | BAR、ATU、HDMA、NPU DMA、mailbox、中断、固件/模型加载接口及对应版本 |
| 错误行为验证范围 | 原需求文档提到错误行为，本轮只明确首版功能优先 | 首版必需的功能错误处理，与后续错误注入、链路异常等建模范围如何划分 |

Host CPU 具体型号、KVM 支持以及多 switch/NTB 均不是首版阻塞项。性能相关能力已明确延后，但这不等于取消正常功能流程中的错误状态和处理需求。

## 6. 与原需求文档的差异及对齐事项

1. **NPU 范围已扩大。** 原文前两部分及 3.2 节采用单 NPU 核、基础 NI900/DMA 的最小能力表述；最新讨论明确首版单 die NPU 模型不裁剪，后续详细设计需按这一结论对齐。不能据此直接推定完整模型的核数或组件清单。
2. **DMA 模块已明确区分。** 原文采用通用 DMA engine 描述，3.4 节还允许 NPU/MCU 共享或分别使用 DMA；最新讨论明确必须有 NPU DMA 和 PCIe HDMA，MCU DMA、HSDMA 可以没有。
3. **首版不承担性能仿真目标。** 原文第 1 节同时列出 transaction、带宽、延迟、拥塞和错误行为；最新讨论明确第一版功能优先，性能相关能力下一步再做。错误行为的具体覆盖仍待细化。
4. **多 die 是后续阶段。** 原先暂不建模卡内 8 die 拓扑的结论仍适用于首版；后续新增每卡 8 die、总计 64 die 的演进目标，不能并入首版承诺。
5. **软件兼容和运行方式已进一步明确。** Host 需要运行 Linux，优先按真实硬件对齐既有驱动/demo，device 侧运行 runtime。原文关于“不需要模拟真实指令”或 MCU ISA 的抽象假设，仍需根据实际固件/runtime 的执行需求核实，不能据此认定已有二进制可直接运行。
6. **集成方案仍需设计。** 使用 QEMU EP 连接既有 simulator、通过 socket 通信是提出的方案，尚未在对话中完成技术定案。

原需求文档保留作为基础材料；后续修订时，应以上述最新决策为输入，并逐项确认详细接口和验收条件。
