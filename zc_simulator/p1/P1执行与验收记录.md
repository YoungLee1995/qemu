## 1. 本轮做了什么

原 P0 能在一个 Spike 内执行任务，stage1 能通过 socket/FIFO 做实验连接。本轮增加独立 `zc-pcie-p1` EP，把 QEMU 和 Spike 的 DDR0/DDR1 映射到**同一组稀疏 memfd**，并让 Host BAR 与 MCU/NPU 访问同一个 mailbox 寄存器 backing。固件加载、CPU 与 NPU 模型继续走原模拟内存接口，不用 Host Python 代算结果。

沿用已调试的 firmware/dispatcher，新增独立的接入测试 MCU/NPU 程序，初始化后发布真实软件 ready。Host 通过 BAR 写包和 mailbox SEND；MCU 校验、NPU 执行原 Tensor 指令并等待原 fence，再发布结果。连续三次执行、五笔非法拒绝后才用 STOP 结束进程。该测试程序不替换业务 runtime，也没有将实验包格式冻结为正式工具链 ABI。

Host demo 按源码复制到 evidence 再打 [适配补丁](host-demo.patch)：Linux 6.12 `class_create` API、IRQ handler 的 `pci_dev` 上下文、可测试的 IRQ 计数，应用移除未使用却强制分配的 hugepage，并将 shell `ls` 发现改为 `opendir/readdir`。`simulator/host-demo` 原文件没有修改。来宾实际加载模块，完成设备发现、BAR2/BAR4/coherent mmap 和 MSI-X handler 验证；不是只编译成功。

reset 通过共享 epoch 请求旧后端在调度边界退出；launcher 回收旧进程和监督线程后再清理状态、重启后端。另用监督线程在后端异常退出时撤销 alive，QEMU 撤销 ready 并拒绝新输入。所有测试等待有上限；这仍是验收 runner 的编排，不是已部署的常驻管理服务。

## 2. 代码归属

| 文件 | 作用 |
| --- | --- |
| `qemu/hw/misc/zc-pcie-p1.c` | PCIe function、软件 BAR profile、32 MSI-X、共享映射、ready/reset/错误可见性 |
| `simulator/riscv-isa-sim/riscv/devices.h/.cc` | 可选 `shared_mem_t`，精确 FD 长度检查和防溢出边界检查；原私有内存路径保留 |
| `simulator/riscv-isa-sim/spike_main/spike.cc` | `--p1-ddr0-fd/--p1-ddr1-fd`；须成对提供，仅支持单 chip/单 die |
| `simulator/riscv-isa-sim/riscv/mbox.cc` | 可选共享寄存器访问、原子 STATUS/INTEN/DATA/SEND、模型线程更新 ECLIC、epoch 停止 |
| `simulator/riscv-isa-sim/smart/sm_main.cc` | 模型调度中调用 mailbox tick；共享模式每 256 模拟周期检查变化 |
| `p1/runtime/` | 独立接入测试夹具，实际 MCU0/NPU0 初始化和 Tensor 执行 |
| `p1/run_p1.py`、`guest-test.c` | Linux 任务与 qtest 生命周期验收、构建/日志/哈希留档 |
| `p1/run_faults.py` | 错误 FD、ready 超时、两 function backing 隔离、BAR 边界、原共享中断回归 |
| `p1/build_host_demo.py`、`host-demo.patch`、`host-probe.c` | 固定依赖的 Host demo 适配构建、coherent mmap 和 MSI-X 测试 |

Host BAR mailbox 的寄存器值只有一份，IRQ 状态由 simu 模型线程持有。QEMU 不直接修改 hart/ECLIC；QEMU MMIO 回调不等待跨进程 RPC。共享模式要求小端宿主和无锁 u32 原子。Host/后端均只承诺对齐 32 位 mailbox 访问。

## 3. 自动验收及证据

最终 Host demo 联合运行：[run-1793096200685406105](evidence/run-1793096200685406105/results.json)，**21 项检查全部通过**。输入/构建产物/相关源码等 32 个文件的 SHA256 见同目录 [manifest](evidence/run-1793096200685406105/manifest.json)。主要结果：

| 检查 | 观察到的结果 |
| --- | --- |
| Linux 枚举/资源 | `16c3:abcd`；BAR0=64KiB，BAR2=4MiB，BAR4=512MiB；经过 root port/switch；IOMMU 启用且分组 |
| 驱动/应用 | 成功创建 `/dev/test_dma_0`，2MiB coherent mmap 首尾可读写；`list-devices` 发现一个 active EP，BAR2/BAR4 与 DMA 均 mmap 成功 |
| MSI-X | 32 vectors；vector0 实际 handler；vector31 mask 时不投递且 PBA 置位，unmask 后恰好投递一次并清 PBA |
| 双侧共享 DDR | 来宾读到固件字节；Host 写 DDR0 的值由 launcher 在同 backing 读取；Host 经 DDR1 写任务，MCU/NPU 消费；NPU 结果经同 backing 返回 Host |
| 常驻任务 | 三笔真实 Tensor 执行、五笔非法请求拒绝；ID/状态/序号/执行计数一致；STOP 后后端正常退出 |
| 结果完整性 | 每次全部 33792 字节与固定旧输出相同；不是只检查 magic 或输出长度 |
| mailbox | early SEND 保留 pending，INTEN 不清 pending，W1C 清除，SEND 读 0；任务使用共享 DATA/SEND |
| 不支持的 DMA | 文件 trigger 明确 error=3，不置假 done |
| 空闲 reset | 旧后端退出 75、回收后无继续写、ready 撤销；重启后再次软件 ready；MSI-X PBA 清除 |
| 异常退出 | 后端 kill 后 ready 撤销，新任务区写被拒绝，原数据不变 |

独立异常及共享中断：[faults-1793096215346651316](evidence/faults-1793096215346651316/results.json)，**11 项全部通过**：ready 超时并回收后端；QEMU/Spike 拒绝错误 FD 长度；Spike 拒绝只提供一个 DDR FD；两 function 的 BAR2 末字读值不同；BAR2 超出 2MiB aperture 的读写报错且 guard 不变；另一 function 错误状态不受影响；原 MCU0↔NPU3 和双 MCU→NPU0 用例在共享 mailbox 模式下输出逐字节一致。

## 4. 失败记录与构建边界

所有失败保留在 evidence：早期 mailbox 每周期刷新全部 IRQ 导致 STOP 回收超时，改为周期检查变化；qtest 曾将 512MiB BAR4 放在非对齐地址，已改为 `0x100000000`；Host 应用曾在 `popen("ls …")` 报 ENOMEM，已改直接目录枚举。以上最终用例均重跑通过。

`run-1793096081305220405` 在进入 `/init` 前出现 Linux `timer doesn't work through Interrupt-remapped IO-APIC` panic。同一配置随后完整通过于上述最终运行；**启动稳定性问题尚未定位关闭**，不自动重试掩盖。当前保留 `intremap=on`，失败必须留档，后续需单独调查 TCG/来宾定时器路径。

Host module 使用固定内核 `6.12.114-0-lts` 对应 headers/symvers，APK 来源与 SHA256 保存在 `evidence/host-module/manifest.json`，联合运行也哈希了该 manifest 和模块。宿主 GCC11 与内核 GCC14 不同，本轮内部调试构建省略插件/自动变量初始化并替换 alignment 参数，BTF 无 vmlinux 时跳过，未签名模块会 taint 来宾内核。这证明当前实验的 probe/mmap/IRQ 可运行，不是发布构建、hardening 等效或完整驱动健壮性验收。原 demo 的热拔插/mmap 生命周期、minor 回收等问题仍需后续治理。

QEMU 新设备 checkpatch 为 0 errors/0 warnings；Python 编译检查及两个仓库的 `git diff --check` 通过。最终 manifest 对应的全部文件哈希复核一致。源码仅用于内部实验，遵守 QEMU 的 AI 内容 provenance 约束，不用于 upstream 投稿。

## 5. P1 剩余开发步骤

| 顺序 | 工作包 | 当前状态与下一步验收 |
| --- | --- | --- |
| 1 / P1-01 | 唯一共享 DDR | P1-A 已实现两区域共享、固件/任务/结果可见性；补充全内存端点/非法宽度和并发矩阵 |
| 2 / P1-02 | 通用桥接会话 | **未完成**；建立 `SOCK_SEQPACKET/SCM_RIGHTS` 协商、身份、版本/能力、配置摘要、request/session/epoch、明确失败及有界超时；不能沿用继承 FD 假装完成协议 |
| 3 / P1-03 | EP 基础 | 软件 profile 的 ID/BAR/Bus Master/MSI-X 已实现；继续核对真实 BAR 属性、窗口和权限，区分实验/兼容验收 |
| 4 / P1-04 | mailbox | 共享权威状态及原 ECLIC 回归通过；继续补高频并发 SEND/INTEN/W1C 与非法宽度的压力和错误判据 |
| 5 / P1-05 | 软件服务 | 当前独立夹具连续任务通过；把通用控制桥接与既有业务 runtime 入口衔接，保留实际软件 ready，不能只以进程存在置 ready |
| 6 / P1-06 | 生命周期 | runner 的启动超时/异常退出/空闲reset通过；补独立常驻服务中的启动失败、断连、重复reset、会话清理和重启任务；调查来宾启动 panic |
| 7 | P1 总验收 | 原矩阵所有适用项关闭并冻结 profile 后，才把 `p1_full_exit` 改为 true；本轮保持 false |

P2 的 HDMA、NPU 外部 DMA、Host file IPC/IOVA 权限服务及在途 DMA reset，仍依原方案单列；本轮没有把它们提前纳入已实现项，也不因缺这些功能回退 P0 结论。

当前直观流程就是：**启动同一组共享内存 → MCU/NPU 真正初始化 → Linux 发现设备 → Host 写包并敲 mailbox → MCU 分发 → NPU 真算 → Host 读结果 → 再提交 → STOP；reset 则先收掉旧后端，再重建服务。** 现在已经能复现这条流程，下一步重点从一次验收编排提升到可协商、可恢复的常驻接入服务。
