## 1. 为什么此前不能关闭，现在补了什么

此前 QEMU/Spike 只是由验收脚本分别继承 FD 并启动，脚本负责 reset 和回收。这能证明共享数据路径，但不能证明协议兼容检查、未知会话拒绝、服务断连或超时恢复。原计划的 P1-02 与部分 P1-06 尚未实现，因此当时必须保持 `p1_full_exit=false`。

本轮 QEMU 新增 `backend-socket/config-sha256/card-id/session-timeout-ms` 配置，自行创建三个 sealed memfd，经 Unix `SOCK_SEQPACKET + SCM_RIGHTS` 交给 simulator 中的常驻服务。服务按版本、能力、card/session/epoch/request、固定配置摘要及 FD 大小/区域/seals 校验，成功后才启动 Spike。软件实际初始化才返回 ready；握手成功和后端进程存在均不能替代它。

服务可以持续接收新会话。正常 reset 在旧后端 wait/reap 后返回 QUIESCED/outstanding=0，再更新 epoch、清理状态并重新启动；断连及启动/ready/heartbeat 超时均有错误和清理。QEMU socket 非阻塞，不在 BAR 回调等待 RPC；MCU/NPU 的 hart/ECLIC 仍归原模型调度线程。Spike 增加可选父进程退出保护，服务被 SIGKILL 时也停止旧 Spike；新会话分配全新 backing，旧 FD 无法写到新内存。

## 3. 冻结的软件 profile 与原设计的落实方式

1. 地址跨度、BAR布局、内部mailbox与实验服务区沿用 [P1 README](README.md) 的显式软件profile。QEMU拥有PCIe/MSI-X和共享FD，simu拥有模型执行及ECLIC；没有两份DDR或mailbox镜像。真实芯片未确认的BAR属性不转写成硬件事实。
2. 控制帧沿用P0目标头：magic=`0x5a435030`、version=1、48字节，payload上限64KiB。caps=15表示共享DDR/mailbox/reset/stop。HELLO同时协商固定配置摘要；request单调递增并对应应答，session每次重连随机生成，epoch在同会话reset递增。未知/重复/旧会话请求失败，不缓存并重放已执行请求。
3. P1只实现当前需要的HELLO、MEM、START、READY、QUIESCE、RESET、STOP、PING及ERROR。原矩阵中的REG代理/外部DMA消息依赖P2的PCIe寄存器代理、引擎和公共访问服务，本轮未声明该能力；未知消息拒绝。mailbox直接操作唯一共享原子状态，不额外发同步REG RPC。后端调度边界周期重读状态，因此P1无需新socket线程唤醒hart或维护第二份寄存器状态；P2异步continuation和消息泵仍按原设计实施。
4. P1-A继承FD入口保留作底层回归；完整验收必须经过socket服务，不能仅运行旧脚本就标记完整P1通过。子项脚本的 `p1_full_exit=false` 表示它们只能证明子范围；唯一完整出口由 `run_full.py` 聚合所有结果后置true。
5. 当前业务入口证据仍是独立接入夹具，复用原firmware/dispatcher及NPU Tensor/fence，并非将实验包固定成正式工具链ABI。业务runtime自身保持原实现；未来更多应用的兼容覆盖单列，不以本次单样例代替。

```bash
python3 qemu/zc_simulator/p1/run_full.py
```

最终证据与具体计数在本节末附表中。验证内容包括：

- 两个DDR实际跨度的load/store/contents同backing，跨页、末尾合法访问、`UINT64_MAX`附近溢出和超长拒绝。

## 5. 来宾启动问题及适用范围

P1-A 曾遇到默认TCG计时配置下 Linux `timer doesn't work through Interrupt-remapped IO-APIC` panic。本轮将验收环境显式固定为 `-icount shift=3,align=off,sleep=off`，保持IOMMU与中断重映射启用，连续五次通过。P1完成结论限定于此运行配置；默认计时环境的历史panic根因仍未定位，不能宣传为所有QEMU启动配置都已稳定。若后续更换计时/CPU配置，需重新回归。

输出仍按旧simu参考逐字节一致，不表示数值golden已通过。原MoE有效区322/1122个BF16位值不同、最大绝对误差1.0及未批准容差的事项保留。Host模块仍为固定headers/symvers下的内部GCC兼容调试构建，未承诺发布hardening等效或热拔插安全性。

**P1关闭不包含**HDMA、Host file-load/get-result/BootROM固件传输、NPU外部DMA、IOVA权限矩阵、P2P、八卡业务运行、在途DMA reset、迁移或性能精度。下一阶段按P2实施公共PCIe访问服务、两类独立DMA和地址转换/错误完成验收。
