# 第一阶段接口决策与待办清单

本文冻结当前内部实验接口，不代表真实硬件 ABI。需求方已授权在真实工具链包和命令 runtime 尚未提供时先实现假包。

## 1. 已确定的实验架构

```text
QEMU x86 Q35 / TCG / 来宾 Linux / Intel IOMMU
  → Root Port → 一个 switch → 下行端口 → zc-pcie-sim EP
  → QEMU chardev 非阻塞 Unix socket
  → Python simu_bridge（独立进程）
  → FIFO / 既有 sm_file MMIO
  → 单 die Spike，MCU0 实验 runtime + NPU0 常驻执行器
  → 原 Tensor 指令 / scheduler / 功能模型
```

当前一套 QEMU、一个桥接进程、一个完整单 die simulator 进程。单 die 保留四个 NPU 模型，业务只路由到 core0。MCU0 hart1、NPU0 hart16，hart0 保留 firmware 启动职责。

八端口验证实例化八个 EP，但只有一个连接真实 simu，其余连接空 chardev，只验证枚举与 BAR 分配。该结果不是八卡业务功能交付。

## 2. EP 配置与 BAR0

内部实验 PCI ID 为 `1234:11f0`，PCIe EP，revision=1，BAR0 为 64 KiB 非预取 32 位 MMIO。此 ID 不是已获分配的产品 ID。当前全部访问为对齐的 32 位 little-endian；未实现真实设备配置空间、ATU、HDMA 或 NPU DMA 的 PCIe 映射。

| BAR0 偏移 | 方向 | 含义 |
| --- | --- | --- |
| `0x00` | R | 标识 `0x5a435031` |
| `0x04` | R | 实验接口版本 1 |
| `0x08` | R | 状态：0=idle，1=busy，2=transport done，3=transport error |
| `0x0c` | R | 传输错误：1=超时，2=未连接/断连，3=响应协议错误 |
| `0x10` | W | 写 1 提交；非 idle 时拒绝并计数 |
| `0x14` | R | INTx pending |
| `0x18` | W | ACK：非 busy 时清除状态、错误、响应长度和 IRQ |
| `0x1c` | R | 完整响应长度 |
| `0x20` | R | 后端连接是否打开 |
| `0x24` | R | busy/done/error 状态下重复 doorbell 的拒绝计数 |
| `0x100..0x19f` | R/W | 160 字节假包暂存区 |
| `0x1000..` | R | 响应头及可选的 33792 字节结果 |

提交时冻结包快照，之后写暂存区不修改在途请求。单 outstanding，必须收到完成并 ACK 后再提交。响应头中的 runtime status 与 EP transport status 分开：runtime 拒绝非法包时，EP 仍可正常收到响应。

## 3. 通信、完成与故障契约

- 业务假包 v1 沿用[假包实验说明](../../simulator/riscv-tests/packet_runtime_test/实验收包执行说明.md)的 160 字节布局；本轮没有另加传输封装，因为每连接严格只有一笔在途请求。
- 响应先接收 32 字节头，再按头内长度收取 0 或 33792 字节结果；校验 magic、命令 ID 和允许长度。非法响应不触发其他命令的成功完成。
- QEMU 使用 `qemu_chr_fe_write` 和接收回调，10 ms 重试部分发送，30 秒实时时钟总超时；MMIO 回调不会等待 socket/FIFO。
- QEMU 回调和定时器在主事件循环更新设备状态。Python 桥接层的同步 FIFO 等待不占用 QEMU 线程，运行失败或断连后关闭 socket，并回收自己启动的 Spike。
- 完整响应到达后才置 done 并拉起 INTx；来宾读完数据写 ACK，IRQ 解除。Linux 测试验证 pending 及 PCI status interrupt 位，尚未实现内核中断处理驱动或 MSI/MSI-X。
- 在途 system reset 关闭连接、清除状态及 IRQ，旧连接响应不能完成新请求。当前无自动重连；reset 后需重建后端连接或重启整套实验。
- EP 明确标为不可迁移；没有迁移、热拔出恢复、FLR、并发命令和完整取消实现。

结果本地内存由 simu 持有，Host/EP 只持有传输副本。初始输入由 firmware 加载，NPU 输出在真实完成后复制到共享 DDR，再由 MCU 回传；本轮尚未把数据搬运替换为 PCIe DMA。

## 4. IOMMU 与 P2P 风险分析

已证明 Linux 开启 Intel IOMMU、EP 归入 IOMMU group，并通过 QEMU 现有 Intel IOMMU 及 IOTLB invalidation 测试。当前 EP 使用 CPU BAR MMIO 提交，不执行设备 Host DMA，因此这些结果不证明 EP 的 IOVA DMA 路径已实现。

源码分析入口：

1. `include/hw/pci/pci_device.h`：`pci_dma_rw()` 访问设备 `bus_master_as`。
2. `hw/pci/pci.c`：`pci_device_iommu_address_space()` 根据 requester 所在总线取 IOMMU 地址空间，否则回落到全局物理空间。
3. `hw/i386/intel_iommu.c`：`vtd_do_iommu_translate()` 处理翻译、权限及 fault。

结论：不能将目标卡 BAR 地址直接交给普通 DMA helper 就声称自动实现了需求中的 IOMMU 旁路。现有 switch 桥层级也不意味着存在目标要求的 credit/TLP 路由模型。

双卡最小实验已确定如下，放在第三阶段实施：

1. 同 switch 挂两个 EP，分别分配 peer BAR，启用 Host IOMMU，核实 Bus Master、BAR 解码和桥窗口。
2. 源卡 Host DMA 经 requester 对应 DMA 地址空间，对有映射 IOVA 成功、未映射/权限错误失败。
3. 源卡 peer 请求仅匹配当前拓扑中启用的目标 BAR，经过受限 peer 路由及目标 inbound ATU；不调用主机 IOMMU 转换，不允许任意 GPA 直访。
4. 不给 peer BAR 建立 IOVA 映射，验证合法 peer 成功而非法 Host DMA 仍失败；同时检查读写数据、源/目标 ID、路径和错误。
5. 关闭 P2P、关闭 BAR/桥窗口、移动 BAR、复位目标卡时，分别验证禁止访问和在途失败行为。

该设计和源码风险分析是第一阶段交付，双卡功能尚未实现；不能全局关闭 IOMMU 规避它。
